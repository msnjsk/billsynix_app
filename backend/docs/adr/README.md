# Architecture decision records

Short records of decisions that are expensive to reverse. Status: Accepted unless noted.

## ADR-001 — Modular monolith on NestJS

One deployable NestJS app, one module per domain (`src/<domain>`). Modules talk through exported
services, never each other's Prisma models directly for writes. Revisit only if a module needs
independent scaling. *Consequence:* simple deploys and transactions across domains (a sale writes
sales, inventory and cash in one transaction).

## ADR-002 — PostgreSQL + Prisma, money as Decimal

PostgreSQL 16 is the system of record; Prisma for schema, migrations and typed queries.
`numeric(12,2)` money, `numeric(12,3)` quantities, handled as `Prisma.Decimal` in code; no JS
floats in money paths. Raw SQL allowed for row locking (`SELECT … FOR UPDATE`) and reports, reviewed.

## ADR-003 — Backend lives in `backend/` beside the frontend

Same workspace for now (one founder, shared docs, shared CI). It has its own `package.json`,
`tsconfig`, lockfile and Dockerfile, and is excluded from the Next.js type-check/build. It can be
split into its own repository later without code changes.

## ADR-004 — Tenant isolation: application scope first, RLS as defence in depth

Every query on tenant-owned data goes through a request-scoped tenant context derived from the
access token (`tid` claim, validated against an active membership). Repositories always filter by
`tenantId`; lookups by id use `findFirst({ where: { id, tenantId } })` and return 404 otherwise.
PostgreSQL Row Level Security policies on `app.tenant_id` are added in Phase 2 for tenant tables,
set per transaction with `SET LOCAL`. Cross-tenant tests are mandatory for each module.

## ADR-005 — Auth: short JWT access + rotating refresh tokens

Access JWT (15 min, HS256, claims `sub`, `tid`, `mid`, `sid`), re-validated against the session
row on every request. Refresh token is an opaque `<sessionId>.<256-bit secret>` stored hashed
(SHA-256) in `sessions`, rotated on every use; reuse of an old token revokes the whole family.
Being opaque, refresh tokens need no signing secret (so there is no `JWT_REFRESH_SECRET`).
Browsers hold it in an httpOnly SameSite=Strict cookie; native clients in secure storage.
Passwords and PINs hashed with Argon2id. Sign-in rate-limited per IP; lockout per account/PIN.
Details: `docs/phase-3-auth.md`.

## ADR-006 — Weighted average cost for inventory valuation

Average cost per (store, product) updated on each purchase receipt; sales snapshot the current
average as `cost` for margin reports. FIFO by batch may be added later for pharmacy.

## ADR-007 — Per-counter invoice series with reserved blocks for offline

See `phase-0/01-scope-and-decisions.md §4`. Lets offline counters issue legally valid numbers without
coordination. *Pending GST professional confirmation.*

## ADR-008 — Validation with Zod through NestJS's built-in Standard Schema pipe

The frontend already uses Zod 4. NestJS 12 validates any Standard Schema natively
(`StandardSchemaValidationPipe`, `@Body({ schema })`), and `@nestjs/swagger` turns the same schemas
into the OpenAPI document (Zod ≥ 4.2 exposes `~standard.jsonSchema`). No class-validator DTOs and no
extra library: one schema drives validation, docs and the generated frontend client.

## ADR-009 — ESM, Vitest and current major versions

NestJS 12 is ESM-only, so the backend is ESM (`"type": "module"`, `.js` import suffixes) and tests
run on Vitest (the NestJS 12 default) with Supertest — Jest-compatible API, as the plan requires.
TypeScript stays on 6.x until `@nestjs/swagger` supports TypeScript 7; Prisma on 7.x stable
(8 is still a release candidate). Node 24 LTS in Docker/CI.

## ADR-010 — Uploaded files in S3-compatible object storage

Files (product photos now; documents later) are written through `StorageService`: local disk for
development and single-server installs, any S3-compatible store (AWS S3, Cloudflare R2, MinIO)
otherwise. Buckets stay private; the API checks access and hands out 5-minute pre-signed URLs.
Keys are generated by the API (`t/<tenantId>/…`), never taken from clients, and uploads are
type-checked by their bytes. *Consequence:* the database holds only keys, and moving to another
provider is a configuration change.
